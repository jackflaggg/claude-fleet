# Промпт для сессии архитектурного ревью claude-fleet

Скопировать в новую сессию, открытую в `~/Projects/claude-fleet`.

---

Ты ведёшь архитектурное ревью проекта claude-fleet и готовишь план переработки. Код не пишешь:
результат этой сессии это план в файле `.claude/tasks/architecture-plan.md`, согласованный со мной
по развилкам через AskUserQuestion.

## Что прочитать до выводов

1. `CLAUDE.md` целиком: там карта файлов, инварианты и история решений с замерами. Инварианты
   это ограничения плана, а не предмет спора: без внешних зависимостей в сервере, только
   localhost с проверкой Host и Origin, `hooks/report.sh` без логики и форков, ограниченная
   память любой накапливающей структуры, замеренная цена анимаций и событий, чтение транскриптов
   только при открытом борде, Node 22 без бандлера и без Electron.
2. `.claude/tasks/audit-2026-09-06.md`: аудит с пруфами, что уже починено, что открыто,
   и раздел «Архитектурные наблюдения». Это вход, а не готовый ответ: проверь каждое
   наблюдение по коду сам и добавь то, чего аудит не увидел.
3. Весь код: `server.js`, `state.js`, `liveness.js`, `usage.js`, `guards.js`, `focus.js`,
   `channel/fleet-channel.js`, `public/js/**`, `hooks/report.sh`, `scripts/*.sh`, `test/**`.
   Тесты прогони: `node --test` (ожидается 132 passed).

## По каким критериям оценивать

Оцени текущую структуру и предложи целевую по каждому пункту, с примерами из кода (файл:строка):

- **SOLID**: где нарушен SRP (`server.js` тянет конфиг, персист, SSE-хаб, реестр каналов,
  сканер транскриптов, роутинг, статику), где OCP (добавление маршрута или агента требует
  правок в нескольких местах), где DIP (модули завязаны на `process.env`, `Date.now`, fs напрямую,
  а чистые ядра получают время параметром: как распространить этот приём на остальное).
- **GRASP**: Information Expert (кто должен знать про `STATUS`/`WAIT_REASON`, сейчас три копии:
  `state.js`, литералы в `server.js`, `board-config.js`), Low Coupling / High Cohesion (сервер
  импортирует из `public/js/lib`), Pure Fabrication (какие сервисы стоит выделить: SseHub,
  ChannelRegistry, UsageScanner, StatePersistence, Config), Protected Variations (схема событий
  Claude Code и Codex меняется без нас: где должна быть граница).
- **DDD в масштабе маленькой тулзы**: не тащить тактические паттерны ради паттернов. Выдели
  домен (сессия, карточка, ожидание и его причина, окно лимита, канал ответа) и ubiquitous
  language, который уже есть в CLAUDE.md, и покажи, где код называет то же самое разными словами.
  Bounded contexts на уровне модулей: приём событий, состояние флота, окно лимита, канал ответа,
  фокус, борд. Если DDD-слой не окупается, скажи это прямо и объясни почему.
- **YAGNI**: составь отдельный список того, что делать НЕ надо (DI-контейнер, ORM, фреймворк,
  слой репозиториев над одним JSON-файлом, микросервисы из трёх процессов и т.п.) и почему
  для этого проекта это лишнее.
- **Чистый код**: имена, длина функций, комментарии «почему» против «что», дублирование
  (SSE-хаб и реестр каналов), магические литералы, обработка ошибок (`.catch(() => {})`
  до аудита), места, где комментарий заменяет тест.
- **Тестируемость**: `server.js` тестируется только спавном процесса; предложи фабрику
  `createFleet({ config, clock, fs })` с `{ server, close }` и тонкий entry-файл, чтобы маршруты
  тестировались in-process. Оцени покрытие фронта (сейчас `board-view.js` и `rail.js` без
  тестов, DOM) и предложи дешёвый способ (jsdom ставить или нет: аргументируй).
- **Протокол сервер-борд**: полный снимок на каждое событие против диффов по карточкам.
  Клиент уже держит реестр элементов по id. Оцени цену и выигрыш, учитывая замеры из аудита
  (20 КБ на событие при 20 сессиях) и что дебаунс 50 мс уже стоит.
- **Безопасность и доверие**: localhost-модель, `FLEET_ALLOWED_HOSTS` без аутентификации,
  любой локальный процесс может слать события и PID. Предложи минимальную модель для сценария
  «планшет в LAN» без выхода за инварианты.

## JavaScript или TypeScript

Дай рекомендацию с аргументами, не общими словами: объём кода (~3000 строк JS без фронта
и тестов), отсутствие бандлера как инвариант, `node --experimental-strip-types` / нативная
поддержка типов в Node 22 (проверь, с какой минорной версии и что нельзя: enums, namespaces,
parameter properties), фронт в браузере без сборки (типы там либо JSDoc, либо отдельная
сборка), стоимость для `hooks/report.sh` (ноль, он bash) и для `channel/` (уже есть npm).
Рассмотри и промежуточный вариант: JSDoc-типы плюс `tsc --checkJs` без эмита. Выбор оставь
мне через AskUserQuestion с ценой каждого варианта.

## Формат плана

`.claude/tasks/architecture-plan.md`, не длиннее 20 КБ:

1. Диагноз: 5-10 главных проблем структуры с файл:строка, ранжированные по цене владения.
2. Целевая структура: дерево модулей с одной строкой ответственности на модуль, границы
   и направление зависимостей (что от чего можно импортировать).
3. Список «не делаем» (YAGNI) с причинами.
4. Пошаговый план миграции: шаги такого размера, чтобы каждый ложился отдельным коммитом
   при зелёных тестах и работающем живом борде (он используется ежедневно). Для каждого шага:
   что переезжает, какие тесты добавляются до шага (RED) и как проверить вживую.
   Первые шаги должны давать выигрыш сразу, а не «сначала полгода фундамента».
5. Риски и открытые вопросы для меня.
6. Оценка в часах по шагам.

## Правила сессии

- Утверждение о коде только после чтения кода: файл:строка в каждом пункте диагноза.
- Развилки (JS/TS, дифф-протокол, тесты фронта, модель доверия) не решай сам: собери варианты
  с ценой и спроси через AskUserQuestion, рекомендуемый вариант первым.
- Код не меняй, файлы вне `.claude/tasks/` не создавай.
- Живой сервер борда (порт 4319) и `.fleet-state.json` не трогай; синтетические события
  только в изолированную копию со своим портом и `FLEET_STATE_FILE`.
- Длинное тире не использовать, в тексте плана обычный дефис.
